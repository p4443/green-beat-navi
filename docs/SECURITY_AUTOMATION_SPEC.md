## 1. 設計方針

| 方針 | 内容 |
| :--- | :--- |
| データ最小化 | 個人情報は「そもそも集めない」を第一選択とする。現行の匿名ID方式を本番でも維持する |
| ゼロトラスト | ネットワーク位置を信頼せず、管理操作はすべて個人認証・最小権限・監査ログを必須とする |
| 自動化ファースト | 依存更新、脆弱性対応、証明書更新、デプロイ、バックアップは人の操作を介さず自動実行する。人の役割は「例外の監視」と「major更新の承認」のみに限定する |
| マネージド優先 | OS・ミドルウェアの保守が不要なマネージドサービスの無料枠を優先し、運用コストと人件費を同時に下げる |
| 段階導入 | 互換性リスクのある対策(CSP等)はReport-Only→本適用の2段階で導入する |

## 2. 現状評価と脅威分析

### 2-1. 現状(デモMVP)の資産とリスク

| 資産 | 現状 | 主な脅威 | リスク評価 |
| :--- | :--- | :--- | :---: |
| `/admin` 運営画面 | 認証なし | なりすまし告知、虚偽の中止・緊急情報配信 | **高** |
| QRチェックイン | 署名・期限なしの素URL | QR複製・転送による不正スタンプ、偽QR貼り替えによるフィッシング | **高** |
| 来場者データ | 匿名ID、localStorage のみ | 端末内のみで漏えい面は小さいが、XSS成立時は窃取可能 | 中 |
| 依存パッケージ | 手動更新 | 既知脆弱性の放置、サプライチェーン攻撃 | 中 |
| 配信経路 | LAN内HTTP | 盗聴・改ざん(本番公開時はTLS必須) | 中 |
| ソースコード | 秘密情報なし(現状維持が前提) | 誤コミットによる秘密情報漏えい | 中 |

### 2-2. 脅威シナリオ(STRIDE要約)

- **なりすまし**:第三者が `/admin` へ接続し緊急告知を偽装 → 認証・権限で遮断(3-3)
- **改ざん**:偽QRの貼り替え、HTTP経路での書き換え → 署名付きQR(3-4)、TLS常時化(3-1)
- **情報漏えい**:XSSによるlocalStorage窃取、秘密情報の誤コミット → CSP(3-2)、シークレットスキャン(3-6)
- **サービス妨害**:当日のDDoS・ボットアクセス → CDN/WAF無料枠で吸収(3-1)
- **権限昇格**:運営スタッフ間の越権操作 → RBACと監査ログ(5章)

## 3. サイバーセキュリティ対策設計

### 3-1. 配信・エッジ層

| 項目 | 設計 | コスト |
| :--- | :--- | :--- |
| TLS | CDN側で常時HTTPS化・証明書自動発行・自動更新(人手ゼロ) | 無料 |
| WAF/DDoS | CDN無料枠のマネージドルール+レート制限 | 無料 |
| HSTS | 本番ドメイン確定後、エッジで `Strict-Transport-Security: max-age=31536000; includeSubDomains` を付与(段階導入後にpreload申請) | 無料 |
| `/admin` 保護 | エッジのアクセス制御(例:Cloudflare Access 無料枠)でSSO認証を前置し、アプリ認証(3-3)との二重化 | 無料(50ユーザーまで) |

候補:Cloudflare Free + Vercel Hobby/Cloud Run 無料枠、またはCloudflare + 小型VPS。いずれも月額0円〜1,000円程度で成立する。

### 3-2. アプリケーション層(本リポジトリで実装済み)

`next.config.ts` に以下を実装済み。

| ヘッダー | 値 | 目的 |
| :--- | :--- | :--- |
| `X-Content-Type-Options` | `nosniff` | MIMEスニッフィング防止 |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | 参照元情報の漏えい抑制 |
| `X-Frame-Options` / CSP `frame-ancestors` | `DENY` / `'none'` | クリックジャッキング防止 |
| `Permissions-Policy` | カメラ・マイク・位置情報等を全拒否 | 不要API悪用の防止 |
| `Content-Security-Policy-Report-Only` | self + OpenStreetMapタイルのみ許可 | XSS緩和(段階導入中) |
| `poweredByHeader: false` | — | フレームワーク情報の秘匿 |

**CSP昇格手順(無人化対象外・一度だけ人が判断)**

1. Report-Onlyのまま全画面を実機で巡回し、違反レポートがないことを確認する。
2. `Content-Security-Policy-Report-Only` を `Content-Security-Policy` へ変更する。
3. 将来インライン排除が完了したら `'unsafe-inline'` をnonce方式へ置換する。

### 3-3. 管理画面認証(P0)

| 項目 | 設計 |
| :--- | :--- |
| 認証方式 | パスキー(WebAuthn)を第一とし、Google/GitHub等のOAuth SSOを併用。パスワードは新設しない(漏えい・使い回しリスクの根絶) |
| 実装 | Auth.js(無料・OSS)+ セッションはHttpOnly/Secure/SameSite=LaxのCookie |
| 権限(RBAC) | `全体管理` / `プログラム担当` / `出店担当` / `閲覧` の4ロール。GBN-OPS-001 4-2の判断権限と一致させる |
| セッション | 有効8時間、重要操作(緊急告知・中止)は再認証を要求 |
| 緊急引継ぎ | 全体管理ロールを2名以上に付与し、単一人依存を排除 |
| 監査ログ | 5章参照 |

### 3-4. 署名付きQRチェックイン(P1)

現行の素URL(`/checkin/地点ID`)を次へ置換する。

```text
/checkin/<地点ID>?t=<トークン>
トークン = base64url( 地点ID . 有効期限epoch . 発行枠ID ) . HMAC-SHA256署名
```

- **署名**:サーバー保持の秘密鍵でHMAC署名。鍵はシークレットストアに置き、90日ごとに自動ローテーション(6-5)。
- **期限**:掲示QRは当日有効(開催日の開場〜終了+1時間)。期限切れは再発行画面を案内。
- **防複製**:チェックイン受付時にサーバーで「同一参加ID×同一地点」の重複と、単位時間あたりの取得レートを検査。SNS転載による遠隔取得は、直前チェックポイントとの最短到達時間(徒歩速度)検査で棄却する。
- **運用**:QR画像は `/qr-demo` 相当の運営画面から当日朝に自動再生成・印刷。前日以前のQRは自動失効する。

### 3-5. サプライチェーン防御(本リポジトリ実装分を含む)

| 対策 | 仕組み | 状態 |
| :--- | :--- | :--- |
| lockfileによる固定 | `package-lock.json` + `npm ci` | 済 |
| 既知脆弱性ゲート | CIで `npm audit --audit-level=high`(high以上で自動マージ停止) | 済(`.github/workflows/ci.yml`) |
| 無人依存更新 | Renovate(6-1) | 済(`renovate.json`) |
| 秘密情報混入検知 | CIでgitleaksスキャン | 済(`.github/workflows/ci.yml`) |
| コンテナスキャン | 本番イメージをTrivy(OSS)でCIスキャン(本番化時に追加) | 計画 |
| SBOM | 本番化時にCycloneDXで生成し、脆弱性照合を自動化 | 計画 |

### 3-6. シークレット管理

- 秘密情報(署名鍵、OAuthクライアントシークレット等)はソース・印刷物・QRへ含めず、ホスティング側のシークレットストア(Vercel/Cloud Run/GitHub Environments。いずれも無料枠内)にのみ保存する。
- `NEXT_PUBLIC_` プレフィックスの環境変数はクライアントへ公開されるため、秘密情報を入れてはならない。
- gitleaksのCI常時実行で誤コミットを無人検知する(実装済み)。

## 4. 個人情報管理設計

### 4-1. 基本方針:収集しないことを第一とする

現行の匿名ID方式(`GB-`乱数、氏名・電話・メール不収集)は個人情報保護の観点で最良であり、**本番でも既定として維持する**。これにより:

- 個人データ漏えいリスクと保護法上の義務負担を構造的に最小化できる。
- 同意取得・開示請求・安全管理措置のコストがほぼゼロになる。

### 4-2. データ分類とライフサイクル

| データ | 分類 | 保存先 | 暗号化 | 保持期間 | 削除方法 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 匿名参加ID・スタンプ | 非個人情報(端末内) | 来場者端末localStorage | 端末依存 | 来場者任意 | 来場者が自分で削除可能にするUIを提供 |
| サーバー側チェックイン記録 | 仮名化データ | サーバーDB | 保存時暗号化(マネージドDB標準) | **開催終了後90日で自動削除** | 保持期間超過分をスケジュール処理で無人削除 |
| 集計KPI | 統計情報(非個人) | サーバーDB | 同上 | 無期限(匿名集計のみ) | — |
| 運営アカウント | 個人情報(氏名・メール) | 認証基盤 | 同上 | 退任後30日で自動削除 | ロール剥奪と同時に自動処理 |
| 監査ログ | 仮名化+操作記録 | ログ基盤 | 同上 | 1年 | 自動ローテーション |
| アクセスログ(IP) | 個人関連情報 | CDN/サーバー | 同上 | 30日 | 自動ローテーション |

### 4-3. 個人情報保護法への対応

| 義務 | 対応 |
| :--- | :--- |
| 利用目的の明示 | `/join` の参加開始画面にプライバシーノーティス(利用目的、保持期間、問い合わせ窓口、第三者提供なしの旨)を常設リンクで表示 |
| 同意 | 匿名運用の範囲では同意は不要だが、将来クーポン連携等で個人情報を扱う場合は、取得項目ごとのオプトイン同意UIを追加してから開始する |
| 安全管理措置 | 本章のライフサイクル管理+3章の技術的対策を組織的・技術的安全管理措置として文書化 |
| 漏えい時対応 | 個人データ漏えいのおそれを検知した場合、本人通知と個人情報保護委員会への報告(速報は概ね3〜5日以内)を行う手順を5-3に定める |
| 委託先管理 | CDN・ホスティング事業者は保護法上の委託先に該当し得るため、各社のDPA/準拠認証(ISO27001等)を採用判断に含める |

### 4-4. 禁止事項(運用ルール)

- 運営画面・認証情報・参加者端末画面の撮影・SNS共有の禁止(GBN-OPS-001 7-3を継承)。
- デモ環境・検証環境へ実個人情報を入力しない。
- アンケート等で個人情報を集める場合は、本設計書の改訂と責任者承認を経てから行う。

## 6. 無人自動更新アーキテクチャ

「人を介さない」を、**定常運用に人の操作が一切不要**(人は例外通知の監視とmajor更新の承認のみ)と定義する。この残された「人の役割」は、技術支援期間中は製作者が担い(8-2)、支援終了後にクライアントへ移行する。

```text
[Renovate] --PR--> [GitHub] --CI(lint/typecheck/test/build/audit/gitleaks)--> 全て成功
    |                                                            |
    |  失敗 → PRは残置(人へ通知)                                  v
    +--------------------------------------------------- 自動マージ(main)
                                                                 |
                                              [ホスティング] 自動ビルド・自動デプロイ
                                                                 |
                                       ヘルスチェック失敗 → 自動ロールバック+通知
```

### 6-1. 依存パッケージ(実装済み)

- **Renovate**(`renovate.json`):patch/minor/pin/digest、lockfile保守、脆弱性修正PRを**CI成功を条件に自動マージ**。GitHub Appは無料。
- **品質ゲート**(`.github/workflows/ci.yml`):lint・typecheck・test・build・`npm audit`・gitleaksの全成功を自動マージの必須条件とする(ブランチ保護で必須チェックに指定)。
- **例外**:`next` / `react` 系のmajorのみDependency Dashboardでの人の承認を残す(破壊的変更リスクのため)。それ以外は完全無人。

### 6-2. アプリケーションのデプロイ

- GitHub連携の自動デプロイ(Vercel Hobby / Cloud Run + Cloud Build 無料枠)を使用し、mainへのマージ=本番反映とする。デプロイ作業者は不要。
- ヘルスチェック失敗時は直前リビジョンへ自動ロールバック(プラットフォーム標準機能)。

### 6-3. 基盤(OS・ランタイム)

| 構成 | 自動更新の仕組み |
| :--- | :--- |
| マネージド(推奨) | OS・ランタイムパッチは事業者側で自動適用。利用者側の作業ゼロ |
| 自前VPSの場合 | `unattended-upgrades`(OSセキュリティパッチ自動適用)+ Watchtower(コンテナイメージ自動更新)+ 再起動は深夜帯に自動実行 |

Dockerベースイメージ(`node:lts-alpine`)のdigest更新もRenovateが追従する(実装済み)。

### 6-4. 証明書・ドメイン

- TLS証明書はCDN/ホスティングの自動発行・自動更新に委ね、手動更新を廃止する。
- 期限監視は外部無料監視(UptimeRobot等)で冗長化し、失効30日前に通知のみ行う。

### 6-5. 鍵・シークレットのローテーション

- QR署名鍵(3-4)は「現行鍵+次期鍵」の2本持ちとし、90日ごとにスケジュール実行(GitHub Actions cron)で無人ローテーション。検証は両鍵で行い、切替時の失効を防ぐ。
- OAuthシークレット等は年1回のローテーションをカレンダー化(ここのみ人の操作が残る)。

### 6-6. コンテンツ(運営情報)の更新

- 告知・遅延・混雑等は運営画面からの入力が本質的に人の判断であるため自動化対象外とするが、配信・同期・反映は全端末へ自動伝搬(P0のサーバー永続化と同時に実現)し、「入力以外の作業ゼロ」とする。

### 8-1. リポジトリ所有とクライアント引き渡し設計

**現状**:`p4443/green-beat-navi`(private)で開発する。GitHub仕様によりOrganizationの新規作成はWeb UIのみのため、暫定的に個人アカウント配下へ置く。

**引き渡し方針**:納品先の専用Organization(例:`green-beat-navi-project`)へ **リポジトリTransfer** で移管する。Transferはコミット履歴・Issue・PR・Actions設定・Webhookを無損失で引き継ぎ、旧URLは自動リダイレクトされる。

**引き渡し手順(所要15分程度)**

1. クライアント側(または受託者が代理で)Organizationを作成し、クライアント担当者をOwnerに追加する(2名以上)。
2. `p4443/green-beat-navi` → Settings → Transfer ownership で移管する。
3. 移管先でRenovate Appと必要な外部連携(Vercel/Cloudflare等)を再認可する。
4. シークレット(QR署名鍵・OAuthクライアント等)はTransfer対象外のため、移管先のEnvironmentsへ再登録し、旧鍵は失効させる。
5. ブランチ保護(mainへの直push禁止、CI必須チェック)を移管先で再確認する。
6. 製作者(p4443)は技術支援期間中、移管先のメンバーとして参加を継続する(権限は8-2参照)。支援終了時に権限を外す。

**注意**:コミット履歴の作者名(p4443)は移管後も残るが、これは通常の受託開発と同様であり問題ない。秘密情報が履歴に含まれないことはCIのgitleaksで常時担保する。

### 8-2. 技術支援期間の体制(製作者の継続関与)

引き渡し後も当分の間、製作者(p4443)が技術支援として関与する。無人自動更新アーキテクチャ(6章)で残る「人の役割」は少量のため、支援期間中は製作者が担い、クライアントは判断と承認に専念する。

**責任分担(支援期間中)**

| 役割 | 製作者(技術支援) | クライアント |
| :--- | :---: | :---: |
| Renovate major更新の技術評価・適用 | ◎ 実施 | 報告を受領 |
| CI失敗・自動更新停止時の調査・復旧 | ◎ 実施 | — |
| セキュリティ通知(脆弱性・漏えい検知)の一次対応 | ◎ 実施 | 二次判断(公表・報告) |
| インシデント時の法的報告(個人情報保護委員会等) | 技術情報を提供 | ◎ 報告主体 |
| 運営コンテンツの更新(告知・運行・混雑) | — | ◎ 実施 |
| 管理者アカウントの発行・剥奪 | 助言 | ◎ 決定 |
| 設計書・マニュアルの改訂 | ◎ 実施 | 承認 |

**権限設計(最小権限)**

| 対象 | 製作者の権限 | 備考 |
| :--- | :--- | :--- |
| GitHubリポジトリ | Maintain(通常時)。設定変更が必要な作業時のみ一時的にAdmin | Ownerはクライアント2名以上を維持 |
| 本番シークレット | 原則アクセスなし。鍵ローテーション作業時のみ一時付与→作業後に失効 | 操作は監査ログへ記録 |
| 運営画面(/admin) | 「閲覧」ロール(障害調査用)。運営操作ロールは持たない | 5-1の権限マトリクスに準拠 |
| 本番サーバー/ホスティング | クライアントのチームメンバーとして招待(Owner不可) | 個人アカウント直結の契約にしない |

**連絡・対応水準(目安)**

- 通常問い合わせ:3営業日以内に回答。
- CI・自動更新の停止:検知通知から2営業日以内に着手。
- セキュリティインシデント:検知後24時間以内に一次対応(本番公開期間中)。
- イベント当日:事前合意した時間帯はオンコール待機。

**支援終了(卒業)条件** — すべて満たした時点で権限を返上し、以後はスポット契約とする。

- [ ] クライアント側に Renovate major 承認と CI 失敗時の一次切り分けができる担当者がいる
- [ ] シークレットのローテーション手順をクライアントのみで1回完遂した
- [ ] インシデント対応訓練(通知→切り分け→報告)を1回実施した
- [ ] 本書・操作マニュアルが最新状態である
