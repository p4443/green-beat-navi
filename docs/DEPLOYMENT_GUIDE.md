# GREEN BEAT NAVI デプロイ手順書

## Cloud Run による本番公開・無人自動デプロイ

- 文書番号:GBN-DEP-001
- 版:1.2
- 改訂日:2026年11月27日
- 対象:技術支援・運営管理者
- 関連文書:GBN-SEC-001(セキュリティ設計書)、GBN-CNT-001(コンテンツ編集ガイド)

> 本書の手順を一度実施すると、以後は **main へ push するだけで本番へ自動反映**されます(無人運用)。アプリは Cloud Run 対応検証済みです(PORT 注入・非 root 実行・転送ヘッダーからの QR URL 生成)。

## 1. 構成と費用

```text
GitHub (main) --push--> Cloud Build(自動ビルド) --> Cloud Run(東京) --> 公開URL
     ↑                                                    |
  Renovate / 編集作業                        失敗時は前リビジョンへ切替(ロールバック)
```

| 項目 | 内容 | 費用目安 |
| :--- | :--- | :--- |
| Cloud Run | リクエスト課金・アイドル時0円(min instances 0) | 無料枠:月200万リクエスト・36万GB秒 → **イベント規模なら0円** |
| Cloud Build | 自動ビルド | 無料枠:1日120分 → 0円 |
| 必要なもの | Googleアカウント+請求先登録(無料枠内でも登録は必須) | — |

## 2. 初回セットアップ(所要30分・一度だけ)

### 2-1. Googleプロジェクト作成

1. <https://console.cloud.google.com> にログイン
2. 上部のプロジェクト選択 →「新しいプロジェクト」→ 名前:`green-beat-navi` → 作成
3. 請求先アカウントを関連付け(未登録の場合はカード登録。無料枠内は請求されません)

### 2-2. Cloud Run サービス作成(GitHub連携)

1. 検索バーで「Cloud Run」→「サービスの作成」
2. **「リポジトリから継続的にデプロイする」** を選択 →「CLOUD BUILD の設定」
3. GitHub を認可し、リポジトリ `p4443/green-beat-navi` を選択
4. ブランチ:`^main$`、ビルドタイプ:**Dockerfile**(パス:`/Dockerfile`)→ 保存
5. サービス設定:

| 設定項目 | 値 |
| :--- | :--- |
| サービス名 | `green-beat-navi` |
| リージョン | `asia-northeast1`(東京) |
| 認証 | **未認証の呼び出しを許可**(一般公開アプリのため) |
| 課金 | リクエスト ベース |
| インスタンスの最小数 | `0`(アイドル時0円) |
| インスタンスの最大数 | `2`(コスト暴走防止) |
| メモリ / CPU | 512 MiB / 1 |

6. 「作成」→ 初回ビルドが走り、数分で `https://green-beat-navi-xxxxx-an.a.run.app` 形式の公開URLが発行されます

### 2-3. 動作確認チェックリスト

公開URLをスマートフォンでも開いて確認します。

- [ ] `/` ホームが表示される
- [ ] `/map` で地図タイルとマーカー7件が表示される
- [ ] `/qr-demo` のQRのURLが **公開URL**(`https://...run.app/...`)になっている
- [ ] `/join` → 参加開始 → `/stamps` でSTARTスタンプが付与される
- [ ] ブラウザの「ホーム画面に追加」でPWAとして起動できる
- [ ] `curl -sI 公開URL | grep -i content-security` でCSPヘッダーが返る

### 2-4. 予算アラート(推奨・5分)

1. 「お支払い」→「予算とアラート」→「予算を作成」
2. 金額:`100円`、しきい値 50%/100% で**メール通知**を設定
3. 想定外の課金が始まった場合に即検知できます(無人運用の安全弁)

## 3. 日常運用(完全無人)

| 操作 | 必要な作業 |
| :--- | :--- |
| コンテンツ変更(スポット・プログラム等) | `content.json` 編集 → push。**それだけで本番反映** |
| 依存パッケージ更新 | Renovate が自動PR → CI成功で自動マージ → 自動デプロイ |
| 反映の確認 | Cloud Run コンソールの「リビジョン」で緑チェックを確認 |

## 4. トラブル対応

### 4-1. ロールバック(1分)

1. Cloud Run → サービス →「リビジョン」タブ
2. 正常だった前のリビジョンを選択 →「トラフィックを管理」→ 100% を割当
3. 即座に旧バージョンへ戻ります(ビルド不要)

### 4-2. ビルド失敗時

- Cloud Build の「履歴」でログを確認
- ローカルで `docker build .` が通るか確認(CIと同一のDockerfileを使用)

## 5. 本番ドメイン確定後の作業(任意・後日)

1. Cloud Run →「カスタムドメインをマッピング」またはCloudflare(推奨:GBN-SEC-001 3-1のWAF/CDN構成)を前段に設置
2. 環境変数 `NEXT_PUBLIC_APP_URL` に確定URL(例 `https://navi.example.jp`)を設定
   - Cloud Run →「編集と新しいリビジョンのデプロイ」→「変数とシークレット」
   - ※未設定でも転送ヘッダーから自動判定されるため動作します(検証済み)
3. QR印刷物を確定URLで再生成

## 6. 管理画面認証の有効化(本番公開時は必須)

環境変数を設定すると `/admin` に個人アカウント認証(GitHub OAuth+許可リスト)が有効になります。**未設定の間はデモモード(認証なし)**ですが、運営状態は操作者のブラウザ内(localStorage)にのみ保存されるため、第三者が開いても他の来場者の画面には影響しません。サーバー永続化(B-3)を導入する際は本章の認証有効化が**必須**です。

### 6-1. GitHub OAuth App の作成(5分)

1. <https://github.com/settings/developers> →「OAuth Apps」→「New OAuth App」
2. 入力値:

| 項目 | 値 |
| :--- | :--- |
| Application name | `GREEN BEAT NAVI Admin` |
| Homepage URL | 公開URL(例 `https://green-beat-navi-xxxxx-an.a.run.app`) |
| Authorization callback URL | `公開URL/api/admin/auth/callback` |

3. 作成後、「Client ID」を控え、「Generate a new client secret」でシークレットを発行

### 6-2. Cloud Run への環境変数設定

「編集と新しいリビジョンのデプロイ」→「変数とシークレット」で以下を設定します。シークレット類は環境変数への直書きを避け、**Secret Manager 連携**を使用してください。

| 変数 | 値 | 備考 |
| :--- | :--- | :--- |
| `AUTH_SECRET` | ランダム64文字(`openssl rand -hex 32` で生成) | **シークレット管理** |
| `ADMIN_GITHUB_CLIENT_ID` | OAuth App の Client ID | |
| `ADMIN_GITHUB_CLIENT_SECRET` | OAuth App の Client Secret | **シークレット管理** |
| `ADMIN_USERS` | `p4443:admin,tanaka:program,sato:spots,suzuki` | GitHubユーザー名:ロール。ロール省略時は閲覧のみ |

ロール:`admin`(全体管理)/`program`(プログラム担当)/`spots`(出店担当)/`viewer`(閲覧)— GBN-SEC-001 5-1 の権限マトリクスに対応。全体管理は2名以上に付与してください。

### 6-3. 動作確認チェックリスト

- [ ] `/admin` が「運営ログイン」画面になる(デモ画面が出ないこと)
- [ ] 許可リストのアカウントでログインでき、ユーザー名とロールが表示される
- [ ] 権限外のセクションが無効化(灰色)になる
- [ ] 許可外アカウントは「権限がありません」で拒否される
- [ ] Cloud Logging に `admin-audit` のログイン記録が残る

## 7. サーバー永続化・複数端末同期の有効化

環境変数 `OPERATIONS_STORE` を設定すると、運営画面の変更(告知・運行状態・混雑)が**すべての端末の来場者画面へ自動反映**されます(約15秒間隔+画面復帰時に同期)。未設定時は従来の端末内デモです。

| 値 | 用途 | 特性 |
| :--- | :--- | :--- |
| `memory` | LANデモ・リハーサル | 追加設定ゼロで複数端末同期。**サーバー再起動で初期化**。Cloud Runではインスタンス最大数を1にすること |
| `firestore` | 本番 | Cloud Firestoreに永続化。再起動・スケールに耐える。無料枠内(1日5万読取) |

### 7-1. 本番(Firestore)の有効化手順

1. Google Cloud コンソール →「Firestore」→「データベースを作成」
   - モード:**ネイティブ モード**、ロケーション:`asia-northeast1`
2. Cloud Run の環境変数に `OPERATIONS_STORE=firestore` を追加してデプロイ
   - 認証は Cloud Run のサービスアカウントを自動使用(**シークレット不要**)
   - 権限エラーになる場合は、サービスアカウントへ「Cloud Datastore ユーザー」ロールを付与
3. 管理画面認証(6章)が**必須**です。認証構成時、運営操作APIはセッション+ロールを検証し、操作は監査ログへ記録されます

### 7-2. 動作確認チェックリスト

- [ ] 管理画面で告知を配信 → **別の端末**の来場者画面にバナーが表示される(最大15秒)
- [ ] 権限外ロールの操作が「権限がありません」で拒否される
- [ ] Cloud Logging に `admin-audit` の `operation` 記録が残る
- [ ] Cloud Run を再デプロイしても状態が保持される(firestoreのみ)
